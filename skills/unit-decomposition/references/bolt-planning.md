# ボルト計画ガイド

## ボルトとは

ボルト（Bolt）はAI-DLCにおける最小の反復サイクルであり、スクラムのスプリントに相当する。
ただし、スプリントが通常2〜4週間であるのに対し、ボルトは**時間〜日単位**で完了する。
この速度はAI駆動の開発によって実現される。

各ボルトは明確に定義された作業スコープを持ち、
完了時にはテスト済みの動作するインクリメントを生成する。

---

## ボルト計画の原則

### 1. 段階的な価値提供
各ボルトは単独でビジネス価値を提供するか、次のボルトの価値提供に不可欠な基盤を構築する。
「技術基盤だけ作って動くものがない」ボルトは避ける。

### 2. 依存関係の尊重
ストーリー間の依存関係に基づき、前提条件が満たされる順にボルトを配置する。
依存関係のないストーリー群は並行ボルトとして計画できる。

### 3. リスクの前倒し
技術リスクが高いストーリー（複雑度L、未知の技術、外部システム連携）は
早期のボルトに含めて、リスクを早く検証する。

### 4. フィードバックループの短縮
ユーザーにフィードバック可能なインクリメントを生成するボルトを優先する。
内部的な技術コンポーネントだけのボルトは、次のボルトで可視化される計画にする。

---

## ボルトの構成

### ボルト内の活動（構築フェーズで実行）

各ボルトは以下の活動を含む。これらはAIが主導し、開発者が検証する：

1. **ドメイン設計** — ボルト内ストーリーのビジネスロジックをモデル化
2. **論理設計** — NFRと設計パターンを適用してアーキテクチャを定義
3. **コード生成** — AIが実行可能なコードとテストを生成
4. **テストと検証** — AIがテストを実行し、開発者が結果を検証

### ボルトのサイズ感

| ボルトサイズ | ストーリー数 | 想定期間 | 適用場面 |
|------------|------------|---------|---------|
| 極小 | 1件（S） | 数時間 | 単独で完結する小さな機能 |
| 小 | 1〜2件（S〜M） | 半日〜1日 | 一般的なボルト |
| 中 | 2〜3件（S〜M） | 1〜2日 | 関連性の高いストーリー群 |
| 大 | 3〜4件（M含む） | 2〜3日 | 複雑な機能の一括構築 |

L複雑度のストーリーは、可能であれば1ストーリー1ボルトとする。

## ボルトスケジュールの表現

### タイムラインビュー

並行実行可能なボルトと順次実行が必要なボルトを可視化する：

```
時間軸 →
Unit-1: [Bolt-1.1: 基盤構築] → [Bolt-1.2: コア機能] → [Bolt-1.3: 統合テスト]
Unit-2: [Bolt-2.1: 基盤構築] → [Bolt-2.2: 表示機能]
Unit-3:                         [Bolt-3.1: 管理機能]  ← Unit-1,2完了後
```

### クリティカルパス

全体の最短完了経路を特定する。クリティカルパス上のボルトは遅延が全体に波及するため、
リソース配分とリスク管理を重点的に行う。

```markdown
## クリティカルパス
Bolt-1.1 → Bolt-1.2 → Bolt-3.1 → 全体完了
合計想定期間: {X}日
```

## ユニットとボルトの関係

1つのユニットは**1つ以上のボルト**で構成される。

- **小さなユニット（ストーリー1〜2件）** → 通常1ボルトで完了
- **標準的なユニット（ストーリー3〜5件）** → 2〜3ボルトに分割
- **大きなユニット（ストーリー6件以上）** → 3〜5ボルト。ユニット分割も再検討

ボルトの切り方の考え方：
- 基盤となるストーリー（他のストーリーが依存する）を最初のボルトに
- ユーザー向けの価値が見える機能を2番目以降のボルトに
- テスト・統合・最適化を最後のボルトに

---

## 並行ボルトの計画

複数チームが参加する場合、ユニット間で並行ボルトを計画できる。

並行実行の条件：
- ユニット間に直接の依存関係がない、または統合仕様が事前に合意されている
- 共有リソース（環境、テストデータ等）の競合がない
- 各ボルトの完了条件が独立して検証可能

並行度を上げすぎると統合時のリスクが増大するため、
統合ボルト（複数ユニットの結合テスト）をスケジュールに含める。

---

## プレゼンテーション層チェック

ボルト計画の策定時に、UIを含むプロジェクトで統合ボルトの計画漏れを防ぐためのチェックを実施する。

### チェックリスト

以下の質問に順番に回答し、結果をボルトスケジュールに反映する:

**1. UIの有無:**
このプロジェクトはユーザーインターフェース（Web、モバイル、CLI等の画面）を含むか？
- **No** → チェック完了（API/バッチ/ライブラリプロジェクト）
- **Yes** → 以下を継続

**2. プレゼンテーション層の所在:**
各ユニットのストーリーにUI操作・画面表示に関する受け入れ基準が含まれるか？
- 含まれるユニットを列挙する
- 各ユニット内のボルトでUI実装が完結するか確認する

**3. UI統合ボルトの要否:**
複数ユニットのドメインロジック出力を統合して1つのUIを構成する必要があるか？
- **Yes** → 「UI統合ボルト」をボルトスケジュールに追加する
- **No** → 各ユニットのボルト内でUI実装が完結するため追加不要

**4. UI統合ボルトのスコープ定義（必要な場合）:**
UI統合ボルトには以下を定義する:
- 統合対象: どのユニットの出力を統合するか
- 前提条件: 依存する全ドメインボルトの完了
- 完了条件: ブラウザ/クライアントでの画面表示確認を含める
- DOM操作・テンプレート・CSS等のプレゼンテーション層コードの実装範囲

### UI統合ボルトの例

```markdown
### Bolt-X.Y: UI統合

**スコープ:**
- Unit-1〜3のドメインロジック出力をHTMLテンプレートに統合
- 画面遷移の実装
- CSS/スタイリングの適用

**前提条件:**
- Bolt-1.1〜1.3, Bolt-2.1〜2.2 完了・マージ済み

**完了条件:**
- ブラウザで全ストーリーの主要シナリオが手動で操作できること
- 既存ユニットテストが全件パスし続けること（リグレッションなし）

**想定期間:** 半日〜1日
```
