# AI-DLC ユニット分解スキル

## トリガー条件

以下の場合にこのスキルを使用する：
- ユーザーが「ユニット分解」「ストーリーをユニットにグループ化」「ユニットに分ける」「AI-DLCのユニット」「ボルト計画」「作業単位に分割」「独立して構築できる単位に分けたい」と言及した場合
- ユーザーストーリー計画スキル（aidlc-user-stories）の完了後に自然に続くフェーズ
- ユーザーストーリーの作成自体は別スキル（aidlc-user-stories）の範囲

## このスキルの目的

AI-DLC（AI-Driven Development Lifecycle）の構想フェーズにおいて、
ユーザーストーリーを**独立して構築・デプロイ可能なユニット**にグループ化し、
各ユニットの**ボルト（反復サイクル）計画**を提案する。

AI-DLCの「会話の方向を逆転させる」原則に従い、**AIがユニット分解案を主導し提案する**。
人間はAIの提案を検証・調整する承認者として機能する。

## 前提知識

ユニット分解の原則と判断基準の詳細は `references/decomposition-principles.md` を参照。
ボルト計画の立て方は `references/bolt-planning.md` を参照。

---

## 入力

このスキルは、ユーザーストーリー計画スキル（aidlc-user-stories）が生成した
以下の成果物を入力として使用する：

**必須入力：**
- `aidlc-docs/handoffs/to_units.md` — ストーリー一覧、依存関係マップ、フレーバー情報
- `aidlc-docs/story-artifacts/{ストーリーファイル}` — 各ストーリーの詳細

**補助入力（存在すれば読み込む）：**
- `aidlc-docs/requirements/nfr_definition.md` — ユニットのNFR割り当てに使用
- `aidlc-docs/requirements/risk_description.md` — ユニットのリスク割り当てに使用
- `aidlc-docs/requirements/business_metrics.md` — ユニットの優先順位判断に使用
- `aidlc-docs/requirements/ubiquitous_language.md` — DDDフレーバーでの境界判断に使用

入力が存在しない場合は、ユーザーにストーリー情報の提供を求めるか、
aidlc-user-storiesスキルの先行実行を推奨する。

---

## ワークフロー

### ステップ0：入力の読み込みと検証

1. `handoffs/to_units.md` を読み込む。存在しない場合、ユーザーにストーリー情報の所在を確認する
2. ストーリー詳細ファイルを読み込む
3. 補助入力ファイルがあれば読み込む
4. フレーバー（DDD/BDD/TDD）を確認する

入力データから以下を抽出・整理する：
- ストーリー数と領域の分布
- 依存関係の構造（方向と深さ）
- 複雑度の分布
- 優先度の分布

### ステップ1：分解方針の提案

入力データの分析結果に基づき、AIがユニット分解の方針を提案する。
提案には以下を含める：

- **分解の軸** — 何を基準にユニットを切るか（機能領域、ドメイン境界、データ境界、チーム境界など）
- **想定ユニット数** — ストーリー数と依存関係から導出した適切なユニット数
- **並行開発の可能性** — どのユニットが並行して構築可能か
- **トレードオフ** — 分解の粗さ・細かさによるメリット・デメリット

方針はユーザーに提示して承認を得る。フレーバー別の分解観点は
`references/decomposition-principles.md` に従う。

### ステップ2：分解計画の作成

方針の承認後、分解計画を `aidlc-docs/plans/unit_decomposition_plan.md` に保存する。

```markdown
# ユニット分解計画

## 入力サマリー
- 意図: {handoffs/to_units.mdから}
- ストーリー数: {N}件
- フレーバー: {DDD/BDD/TDD}

## 分解方針
{ステップ1で合意した方針の要約}

## 計画ステップ
- [ ] 1. ユニット候補の定義
- [ ] 2. ストーリーのユニットへの割り当て
- [ ] 3. ユニット間の結合度検証
- [ ] 4. 各ユニットのボルト計画
- [ ] 5. 統合仕様の定義
- [ ] 6. 最終レビューと調整

## 確認事項
{ユーザーに確認が必要な判断事項}
```

**計画はユーザーの承認を得てから実行を開始する。**

### ステップ3：ユニット候補の定義とストーリー割り当て

AIがユニット候補を提案し、各ストーリーをユニットに割り当てる。

**ユニットの提案→承認→保存を一連の流れで行う：**
1. AIがユニット候補とストーリー割り当てを提案する
2. ユーザーがレビューし、ユニット境界やストーリー割り当ての調整を指示する
3. AIが修正を反映し、ユーザーの承認を得る
4. **承認されたユニット定義を即座にファイルに保存する**

保存先: `aidlc-docs/design-artifacts/units/unit_{番号}_{ユニット名}.md`

議論と保存を分離しない。承認されたユニット定義がファイルに残っていないと、
後続ステップ（結合度検証、ボルト計画、統合仕様）で参照できなくなる。

各ユニットは以下の情報を持つ：

```markdown
## Unit-{番号}: {ユニット名}

**目的:**
{このユニットが提供するビジネス価値を1〜2文で}

**含まれるストーリー:**
| ID | タイトル | 優先度 | 複雑度 |
|----|----------|--------|--------|
| US-XXX | {タイトル} | {高/中/低} | {S/M/L} |

**ユニットの特性:**
- 凝集度の根拠: {なぜこれらのストーリーが一緒にまとまるのか}
- 外部依存: {他ユニットとの依存関係}
- 独立デプロイ可能性: {はい/条件付き/いいえ}

**関連NFR:**
- {このユニットに特に関係するNFR ID}

**関連リスク:**
- {このユニットに特に関係するリスク ID}
```

フレーバー固有の追記：
- **DDD**: 境界コンテキスト名、コンテキストマップ上の関係（上流/下流/パートナーシップ等）
- **BDD**: ユニット単位の主要シナリオ一覧（受け入れテストスイートの単位）
- **TDD**: ユニット単位のテスト戦略（ユニットテスト/統合テストの境界）

### ステップ4：ユニット間の結合度検証

提案したユニット分解が「疎結合」の原則を満たしているか検証する。

**検証基準：**
- ユニット間の依存関係が一方向であること（循環依存がないこと）
- ユニット間のインターフェースが明確に定義可能であること
- 1つのストーリー変更が他ユニットに波及しないこと
- 各ユニットが独立してテスト可能であること

問題が見つかった場合は、ストーリーの再割り当てまたはユニット境界の調整を提案する。

検証結果を `aidlc-docs/design-artifacts/coupling_analysis.md` に保存：

```markdown
# ユニット間結合度分析

## 依存関係マトリクス
| | Unit-1 | Unit-2 | Unit-3 |
|--------|--------|--------|--------|
| Unit-1 | - | {依存の種類} | なし |
| Unit-2 | なし | - | {依存の種類} |
| Unit-3 | なし | なし | - |

## 循環依存チェック
{循環依存の有無と対処}

## 統合ポイント
{ユニット間で共有するインターフェース/契約の一覧}
```

### ステップ5：ボルト計画

各ユニットに対してボルト（反復サイクル）を計画する。
ボルトの詳細な計画方法は `references/bolt-planning.md` を参照。

各ボルトの定義：

```markdown
### Bolt-{ユニット番号}.{ボルト番号}: {ボルト名}

**スコープ:**
| ストーリーID | タイトル |
|-------------|----------|
| US-XXX | {タイトル} |

**前提条件:**
- {他ボルトの完了等}

**完了条件:**
- {ボルト完了の判定基準}

**想定期間:** {時間〜日の見積もり}
```

ボルトのスケジュール全体を `aidlc-docs/plans/bolt_schedule.md` に保存する。
並行実行可能なボルトを明示し、全体のクリティカルパスを可視化する。

### ステップ6：統合仕様の定義

ユニット間の統合ポイントについて、構築フェーズで交換する統合仕様のテンプレートを定義する。
AI-DLCではモブ構築イベント時にチーム間で統合仕様を交換する。

`aidlc-docs/design-artifacts/integration_specs.md` に保存：

```markdown
# 統合仕様

## Unit-{X} → Unit-{Y}: {統合名}

**インターフェース種別:** {API / イベント / 共有データ}
**データ契約:**
{交換するデータの構造の概要}

**責任境界:**
- 提供側（Unit-X）: {何を保証するか}
- 利用側（Unit-Y）: {何を期待するか}
```

### ステップ7：横断レビューと引き継ぎ

全成果物の横断的な整合性を `aidlc:cross-review` エージェントでレビューし、
不整合を修正した上で、構築フェーズへの引き継ぎ情報を作成する。

#### 横断レビュー（aidlc:cross-review エージェント）

`aidlc:cross-review` エージェントに以下を指示して呼び出す:
- レビュー対象: design-artifacts/units/, plans/bolt_schedule.md, design-artifacts/coupling_analysis.md, design-artifacts/integration_specs.md, story-artifacts/, requirements/
- レビュー観点: TERM_CONSISTENCY, NFR_COVERAGE, AC_COMPLETENESS

レビュー結果を `aidlc-docs/reports/cross_review_report.md` に保存。

#### 構築フェーズへの引き継ぎ情報

横断レビュー完了後、`aidlc:handoff-generator` エージェントを呼び出して
`aidlc-docs/handoffs/to_build.md` に引き継ぎ情報を生成する。

全成果物を `aidlc-docs/manifest.md` に登録する。

prompts.mdにも各ステップの実行記録を追記する（aidlc:user-storiesスキルと同じフォーマット）。

## 対話スタイルのガイドライン

aidlc-user-storiesスキルと同じ原則に従う：

1. **AIが主導する** — 「どう分けましょうか？」ではなく「以下の3ユニットに分けることを提案します。理由は...」
2. **具体的な分解案を先に出す** — 空のユニット枠を渡すのではなく、ストーリーを割り当て済みの案を提示して修正を求める
3. **判断はユーザーに委ねる** — ユニット境界の最終決定、ボルトの優先順序、並行度の判断はユーザーが行う
4. **段階的に進める** — 分解方針→ユニット定義→結合度検証→ボルト計画の順に、各ステップで承認を得る

---

## ありがちな失敗パターンと対策

- **ユニットが大きすぎる** → 1ユニットにストーリー5件以上あれば分割を検討する
- **ユニットが小さすぎる** → ストーリー1件のユニットは他との統合を検討する
- **循環依存** → ストーリーの再割り当て、またはインターフェース抽出で解消
- **統合仕様の曖昧さ** → 具体的なデータ契約と責任境界を定義する
- **ボルトの依存関係の見落とし** → 結合度分析の結果をボルト計画に反映する
- **NFR/リスクのユニット割り当て漏れ** → 横断的NFRは全ユニット共通として明示する
