# AI-DLC フレーバー別ストーリー記述ガイド

AI-DLCは設計技術をコアに統合する。フレーバーによって、ユーザーストーリーの
記述方法と付随する成果物が変わる。

---

## DDDフレーバー（ドメイン駆動設計）

### ストーリー記述の特徴

DDDフレーバーでは、ストーリーの記述にドメインの**ユビキタス言語**を使用する。
ストーリー内の用語はチーム全体で統一された意味を持つ。

#### 追記事項

各ストーリーに以下を追加：

```markdown
**ドメイン用語:**
- {用語1}: {定義}
- {用語2}: {定義}

**関連ドメイン要素（参考）:**
- 集約: {関連する集約候補}
- エンティティ: {関連するエンティティ候補}
- 値オブジェクト: {関連する値オブジェクト候補}
- ドメインイベント: {発生しうるイベント候補}
```

注意：構想フェーズではドメインモデルの完全な設計は行わない。
ここでの記載はあくまで参考情報であり、構築フェーズでのドメイン設計に引き継ぐ。

#### ユビキタス言語の用語集

DDDフレーバーを選択した場合、ストーリー作成と並行して用語集を作成する。
保存先: `aidlc-docs/requirements/ubiquitous_language.md`

```markdown
# ユビキタス言語 用語集

| 用語 | 定義 | 使用コンテキスト |
|------|------|------------------|
| {用語} | {チームで合意した定義} | {どの領域で使用されるか} |
```

### 受け入れ基準の書き方

DDDフレーバーでもBDD的なGiven-When-Then形式を使えるが、必須ではない。
重要なのはドメイン用語で記述し、ビジネスルールを明確に表現すること。

```markdown
**受け入れ基準:**
1. 顧客が購入履歴のある商品カテゴリに属する商品を閲覧した場合、
   関連レコメンデーションが表示される
2. 新規顧客（購入履歴なし）の場合、人気商品に基づくデフォルト
   レコメンデーションが表示される
```

## BDDフレーバー（振る舞い駆動開発）

### ストーリー記述の特徴

BDDフレーバーでは、受け入れ基準を**Given-When-Then**形式で厳密に記述する。
これにより、受け入れ基準がそのまま自動テストのシナリオになる。

#### 受け入れ基準のフォーマット

```markdown
**受け入れ基準:**

**シナリオ1: {シナリオ名}**
- **Given** {前提条件}
- **When** {アクション}
- **Then** {期待される結果}

**シナリオ2: {シナリオ名}**
- **Given** {前提条件}
  **And** {追加の前提条件}
- **When** {アクション}
- **Then** {期待される結果}
  **And** {追加の期待される結果}
```

#### 追記事項

```markdown
**テストシナリオ概要:**
- 正常系: {カバーするシナリオ数}
- 異常系: {カバーするシナリオ数}
- 境界値: {カバーするシナリオ数}
```

### シナリオ作成のガイドライン

- シナリオ名は振る舞いを説明する（「正常」「異常」ではなく具体的に）
- Given節は最小限の前提条件に絞る
- When節は単一のアクションにする
- Then節は検証可能な具体的結果にする
- 1つの受け入れ基準に対して正常系・異常系・境界値のシナリオを含める

## ストーリーベースフレーバー（軽量アプローチ）

### ストーリー記述の特徴

ストーリーベースフレーバーでは、シンプルな受け入れ基準で実装可能な軽量アプローチを採用する。
DDDのようなユビキタス言語の厳密な管理や、BDDのようなGiven-When-Then形式は求めず、
受け入れ基準を番号付きリストで簡潔に記述する。

#### 受け入れ基準の書き方

受け入れ基準はプレーンな番号付きリストで記述する。
ユビキタス言語やGiven-When-Then形式は不要。

```markdown
**受け入れ基準:**
1. ユーザーがログインフォームにメールアドレスとパスワードを入力して送信すると、
   認証が行われダッシュボードに遷移する
2. メールアドレスが未登録の場合、「アカウントが見つかりません」とエラー表示される
3. パスワードを3回連続で間違えると、アカウントが15分間ロックされる
4. ログイン成功時にセッショントークンが発行され、24時間有効である
```

#### 追記事項

各ストーリーに以下を追加（参考情報として）：

```markdown
**コンポーネント候補（参考）:**
- {コンポーネント名}: {責任の概要}
- {コンポーネント名}: {責任の概要}
```

注意：構想フェーズではコンポーネント設計の完全な定義は行わない。
ここでの記載はあくまで参考情報であり、構築フェーズでの設計に引き継ぐ。

### 最適な場面

- シンプルなプロジェクト（ドメイン複雑度が低い）
- アルゴリズムやデータ処理が中心のシステム
- 個人開発や少人数チームでの開発
- プロトタイプや MVP の構築

---

## フレーバー選択のガイドライン

| 観点 | DDD | BDD | ストーリーベース |
|------|-----|-----|-----------------|
| 最適な場面 | 複雑なビジネスドメイン | ステークホルダーとの仕様合意が重要 | シンプルなプロジェクト、個人開発 |
| ストーリーの焦点 | ドメイン概念の正確さ | 振る舞いの明確さ | 実装可能な受け入れ基準 |
| 受け入れ基準 | ビジネスルール中心 | Given-When-Then形式 | 番号付きリスト（プレーン） |
| 構築フェーズへの引継 | ドメインモデル設計へ | シナリオベースのテスト自動化へ | コンポーネントモデル設計へ |
| 追加成果物 | ユビキタス言語用語集 | シナリオ一覧 | コンポーネント候補リスト |

### AI推薦型のフレーバー選択

AIがプロジェクト特性を分析し、最適なフレーバーを推薦する。ユーザーが承認または変更する。

**分析する観点：**
- **ドメイン複雑度**（高/中/低） — ビジネスルールの多さ、エンティティ間の関係の複雑さ
- **ステークホルダー合意の必要性** — 非技術者との仕様合意が重要か
- **プロジェクト規模** — チーム規模、開発期間、ストーリー数

**推薦ロジック：**
- ドメイン複雑度が高い → **DDD推薦**
- ステークホルダーとの仕様合意が重要 → **BDD推薦**
- それ以外（シンプルなドメイン、個人開発、アルゴリズム中心等） → **ストーリーベース推薦**
- 判断がつかない場合 → **DDD**（AI-DLCのデフォルトフレーバー）
