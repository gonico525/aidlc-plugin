# AI-DLC フレーバー別ストーリー記述ガイド

AI-DLCは設計技術をコアに統合する。フレーバーによって、ユーザーストーリーの
記述方法と付随する成果物が変わる。

---

## DDDフレーバー（ドメイン駆動設計）

### ストーリー記述の特徴

DDDフレーバーでは、ストーリーの記述にドメインの**ユビキタス言語**を使用する。
ストーリー内の用語はチーム全体で統一された意味を持つ。

#### 追記事項

各ストーリーに以下を追加：

```markdown
**ドメイン用語:**
- {用語1}: {定義}
- {用語2}: {定義}

**関連ドメイン要素（参考）:**
- 集約: {関連する集約候補}
- エンティティ: {関連するエンティティ候補}
- 値オブジェクト: {関連する値オブジェクト候補}
- ドメインイベント: {発生しうるイベント候補}
```

注意：構想フェーズではドメインモデルの完全な設計は行わない。
ここでの記載はあくまで参考情報であり、構築フェーズでのドメイン設計に引き継ぐ。

#### ユビキタス言語の用語集

DDDフレーバーを選択した場合、ストーリー作成と並行して用語集を作成する。
保存先: `aidlc-docs/requirements/ubiquitous_language.md`

```markdown
# ユビキタス言語 用語集

| 用語 | 定義 | 使用コンテキスト |
|------|------|------------------|
| {用語} | {チームで合意した定義} | {どの領域で使用されるか} |
```

### 受け入れ基準の書き方

DDDフレーバーでもBDD的なGiven-When-Then形式を使えるが、必須ではない。
重要なのはドメイン用語で記述し、ビジネスルールを明確に表現すること。

```markdown
**受け入れ基準:**
1. 顧客が購入履歴のある商品カテゴリに属する商品を閲覧した場合、
   関連レコメンデーションが表示される
2. 新規顧客（購入履歴なし）の場合、人気商品に基づくデフォルト
   レコメンデーションが表示される
```

## BDDフレーバー（振る舞い駆動開発）

### ストーリー記述の特徴

BDDフレーバーでは、受け入れ基準を**Given-When-Then**形式で厳密に記述する。
これにより、受け入れ基準がそのまま自動テストのシナリオになる。

#### 受け入れ基準のフォーマット

```markdown
**受け入れ基準:**

**シナリオ1: {シナリオ名}**
- **Given** {前提条件}
- **When** {アクション}
- **Then** {期待される結果}

**シナリオ2: {シナリオ名}**
- **Given** {前提条件}
  **And** {追加の前提条件}
- **When** {アクション}
- **Then** {期待される結果}
  **And** {追加の期待される結果}
```

#### 追記事項

```markdown
**テストシナリオ概要:**
- 正常系: {カバーするシナリオ数}
- 異常系: {カバーするシナリオ数}
- 境界値: {カバーするシナリオ数}
```

### シナリオ作成のガイドライン

- シナリオ名は振る舞いを説明する（「正常」「異常」ではなく具体的に）
- Given節は最小限の前提条件に絞る
- When節は単一のアクションにする
- Then節は検証可能な具体的結果にする
- 1つの受け入れ基準に対して正常系・異常系・境界値のシナリオを含める

## TDDフレーバー（テスト駆動開発）

### ストーリー記述の特徴

TDDフレーバーでは、各ストーリーに**テスト観点**を明示し、
受け入れ基準をテストケースとして直接実装可能な形で記述する。

#### 追記事項

```markdown
**テスト観点:**
- ユニットテスト: {テストすべき振る舞い/関数}
- 統合テスト: {テストすべき連携ポイント}
- E2Eテスト: {テストすべきユーザーフロー}

**テスト優先度:**
1. {最初に書くべきテスト — 最も重要なビジネスルール}
2. {次に書くべきテスト}
3. {その次}
```

#### 受け入れ基準の書き方

TDDフレーバーでは、受け入れ基準をテスト可能な具体的な条件として記述する：

```markdown
**受け入れ基準:**
1. `getRecommendations(customerId)` が購入履歴のある顧客に対して
   少なくとも3件のレコメンデーションを返すこと
2. `getRecommendations(customerId)` が購入履歴のない顧客に対して
   デフォルトの人気商品リストを返すこと
3. レスポンスタイムが200ms以内であること（100件の商品カタログに対して）
```

### Red-Green-Refactorとの関連

ストーリーの受け入れ基準は、構築フェーズでのRed-Green-Refactorサイクルの
「Red」（失敗するテスト）の出発点になる。そのため、受け入れ基準は
できるだけ具体的かつテスト実装可能な形で書く。

## フレーバー選択のガイドライン

| 観点 | DDD | BDD | TDD |
|------|-----|-----|-----|
| 最適な場面 | 複雑なビジネスドメイン | ステークホルダーとの仕様合意が重要 | 技術的に複雑なロジック |
| ストーリーの焦点 | ドメイン概念の正確さ | 振る舞いの明確さ | テスト可能性 |
| 受け入れ基準 | ビジネスルール中心 | Given-When-Then形式 | テストケース指向 |
| 構築フェーズへの引継 | ドメインモデル設計へ | シナリオベースのテスト自動化へ | テストファーストの実装へ |
| 追加成果物 | ユビキタス言語用語集 | シナリオ一覧 | テスト観点マトリクス |

ユーザーが迷っている場合の推奨：
- ビジネスロジックが複雑なエンタープライズシステム → **DDD**
- 非技術ステークホルダーとの合意形成が重要 → **BDD**
- アルゴリズムやデータ処理が中心 → **TDD**
- 判断がつかない場合 → **DDD**（AI-DLCのデフォルトフレーバー）
