# AI-DLC ユーザーストーリー計画スキル

## このスキルの目的

AI-DLC（AI-Driven Development Lifecycle）の構想フェーズにおいて、
高レベルのビジネス意図をユーザーストーリーと関連成果物に変換するプロセスを支援する。

AI-DLCの核心原則「会話の方向を逆転させる」に従い、**AIが対話を主導する**。
人間が意図を伝えた後、AIが明確化質問を行い、ストーリーを提案し、
人間は承認者・検証者として機能する。

## 前提知識

AI-DLCの構想フェーズ詳細は `references/envision-phase.md` を参照。
フレーバー別（DDD/BDD/TDD）のストーリー記述ガイドは `references/flavor-guide.md` を参照。

---

## ワークフロー

### ステップ0：セットアップ

ユーザーの最初のメッセージから以下を判断する：

1. **意図の有無** — 具体的なビジネス意図が既に示されているか
2. **フレーバー** — DDD/BDD/TDDのどれを使うか（不明なら聞く）
3. **出力先** — ファイル出力が必要か（デフォルトはaidlc-docsフォルダ構造を使用）

フォルダ構造を作成する（存在しない場合）：

```
aidlc-docs/
├── plans/           # 計画ファイル
├── requirements/    # 要件・機能変更文書
├── story-artifacts/ # ユーザーストーリー
└── prompts.md       # 指示の記録
```

**prompts.mdの記録ルール：**
各ステップの開始時に、AIが実行する指示の要約をprompts.mdに追記する。
これにより、セッション全体の意思決定の軌跡が記録される。フォーマット：

```markdown
## ステップ{N}: {ステップ名} — {タイムスタンプ}
- 指示: {実行内容の要約}
- ユーザー判断: {ユーザーが行った主要な決定}
- 結果: {生成された成果物のファイルパス}
```

### ステップ1：意図のキャプチャと明確化

AI-DLCでは「AIが会話を主導する」。意図を受け取ったら、以下の観点で明確化質問を行う。
一度に3〜5個の質問を提示し、ユーザーの回答を待つ。

必ず確認すべき観点：
- **主要ユーザー/ペルソナ** — このシステムの主な利用者は誰か
- **ビジネス成果** — 達成すべき主要なビジネス成果は何か
- **スコープの境界** — 今回のスコープに含めないものは何か
- **既存システムとの関係** — グリーンフィールドかブラウンフィールドか
- **品質属性の優先度** — パフォーマンス、セキュリティ、可用性などの優先順位

質問はドメインに合わせて具体的にする。汎用的・抽象的な質問を避け、
ユーザーの意図から推測できる具体的な確認事項を問う。

### ステップ2：計画の作成

明確化が完了したら、ストーリー詳細化の計画を作成する。
計画は `aidlc-docs/plans/user_stories_plan.md` に保存する。

計画ファイルのフォーマット：

```markdown
# ユーザーストーリー計画

## 意図
（明確化された意図の要約）

## フレーバー
（DDD / BDD / TDD）

## 計画ステップ
- [ ] 1. ペルソナの定義
- [ ] 2. エピック/機能領域の特定
- [ ] 3. 各領域のユーザーストーリーと受け入れ基準の作成
  - [ ] 3.1 領域A のストーリー
  - [ ] 3.2 領域B のストーリー
  ...
- [ ] 4. NFR（非機能要件）の定義
- [ ] 5. リスク説明の作成
- [ ] 6. ビジネス測定基準の定義
- [ ] 7. PRFAQ の作成（オプション — ユーザーに要否を確認）
- [ ] 8. 最終レビューと調整

## 確認事項
（ユーザーに確認が必要な判断事項をここに記載）
```

**重要：計画はユーザーの承認を得てから実行を開始する。**
重要な設計判断を自分で行わない。判断が必要な場合は計画内にメモとして記載し、
ユーザーに確認を求める。

### ステップ3：ストーリーの詳細化（計画の実行）

承認された計画を1ステップずつ実行する。各ステップ完了時に計画ファイルの
チェックボックスを更新する。

各ストーリーは**受け入れ基準とセットで作成する**（別ステップに分離しない）。
ストーリーの文脈が頭にあるうちに受け入れ基準を書くほうが自然で品質が高い。

**ストーリーの作成→承認→保存を一連の流れで行う：**
1. AIが機能領域ごとにストーリー群を提案する
2. ユーザーがレビュー・修正を指示する
3. AIが修正を反映し、ユーザーの承認を得る
4. **承認されたストーリー群を即座にファイルに保存する**

保存先: `aidlc-docs/story-artifacts/{領域名}_stories.md`
（例: `user_data_collection_stories.md`, `recommendation_engine_stories.md`）

議論と保存を分離しない。承認されたストーリーがファイルに残っていないと、
後続ステップ（NFR定義、リスク説明）でストーリーを参照できなくなる。

#### ストーリーの記述フォーマット

フレーバーに応じた記述形式を使う（詳細は `references/flavor-guide.md`）。

**共通フォーマット（全フレーバー）：**

```markdown
## US-{番号}: {タイトル}

**ストーリー:**
{ペルソナ}として、{目的}したい、なぜなら{理由}だから。

**受け入れ基準:**
1. {基準1}
2. {基準2}
...

**NFR関連:**
- {該当するNFR参照}

**リスク:**
- {特定されたリスク}

**優先度:** {高/中/低}
**見積もり複雑度:** {S/M/L}
```

フレーバー固有の追記事項：
- **DDD**: ドメイン用語の統一言語（ユビキタス言語）を明示。関連する集約・エンティティを注記。
- **BDD**: 受け入れ基準をGiven-When-Then形式で記述。
- **TDD**: テスト可能な振る舞いを明示し、テスト観点を受け入れ基準に組み込む。

#### ストーリー品質チェック

各ストーリーは以下のINVEST基準を満たすべき：
- **I**ndependent（独立性）— 他のストーリーに依存しすぎない
- **N**egotiable（交渉可能）— 詳細は議論の余地がある
- **V**aluable（価値がある）— ユーザーに価値を提供する
- **E**stimable（見積もり可能）— 規模を見積もれる
- **S**mall（小さい）— 1ボルト（時間〜日単位）で完了可能な粒度
- **T**estable（テスト可能）— 受け入れ基準で検証できる

AI-DLCでは特に「Small」の基準が重要。従来のスプリント（週単位）ではなく
ボルト（時間〜日単位）で完了可能な粒度にする。大きすぎるストーリーは分割を提案する。

### ステップ4：NFRとリスクの定義

ストーリー詳細化の後、横断的なNFRとリスクを整理する。

**NFRの定義** — `aidlc-docs/requirements/nfr_definition.md` に保存：
- パフォーマンス要件（レスポンスタイム、スループット）
- セキュリティ要件（認証、認可、データ保護）
- 可用性要件（SLA、災害復旧）
- スケーラビリティ要件
- コンプライアンス要件（GDPR、PCI-DSSなど該当するもの）

**リスク説明** — `aidlc-docs/requirements/risk_description.md` に保存：
- 技術リスク（技術的不確実性、依存関係）
- ビジネスリスク（市場変化、要件変更）
- 運用リスク（デプロイメント、モニタリング）

### ステップ5：ビジネス測定基準の定義

意図に追跡可能なビジネスKPIと成功指標を定義する。
AI-DLCでは、構想フェーズの時点でビジネス価値の測定方法を明確にしておく。
これは構築フェーズ以降の優先順位判断と運用フェーズでの効果測定に直結する。

`aidlc-docs/requirements/business_metrics.md` に保存：

```markdown
# ビジネス測定基準

## 主要KPI
| KPI | 現状値 | 目標値 | 測定方法 | 関連ストーリー |
|-----|--------|--------|----------|----------------|
| {KPI名} | {現状} | {目標} | {測定手段} | {US-XXX} |

## 成功指標
- {短期（1ボルト後）の成功条件}
- {中期（全ユニット完了後）の成功条件}
- {長期（運用開始後3ヶ月）の成功条件}
```

### ステップ6：PRFAQ の作成（オプション）

ユーザーにPRFAQの要否を確認する。PRFAQはビジネス意図、機能、期待される利益を
プレスリリース形式で要約した文書であり、ステークホルダーとの整合に有用。

作成する場合は `aidlc-docs/requirements/prfaq.md` に保存：

```markdown
# PRFAQ: {プロジェクト名}

## プレスリリース
{1段落：誰のために、何を、なぜ作るのか}

## FAQ
### Q1: {ステークホルダーが最初に聞くであろう質問}
A: {回答}

### Q2: {技術的な懸念に関する質問}
A: {回答}

### Q3: {ビジネス価値に関する質問}
A: {回答}
```

### ステップ7：横断レビューと引き継ぎ

全成果物の横断的な整合性を `aidlc:cross-review` エージェントでレビューし、
不整合を修正した上で、ユニット分解への引き継ぎ情報を作成する。

#### 横断レビュー（aidlc:cross-review エージェント）

`aidlc:cross-review` エージェントに以下を指示して呼び出す:
- レビュー対象: story-artifacts/ 配下の全ファイル、requirements/ 配下の全ファイル
- レビュー観点: TERM_CONSISTENCY, NFR_COVERAGE, RISK_COVERAGE, KPI_TRACEABILITY, AC_COMPLETENESS

#### 引き継ぎ情報の作成

横断レビュー完了後、`aidlc:handoff-generator` エージェントを呼び出して
ユニット分解への引き継ぎ情報を `aidlc-docs/handoffs/to_units.md` に生成する。

また、全成果物を `aidlc-docs/manifest.md` に登録する（存在しなければ作成）。

## 対話スタイルのガイドライン

AI-DLCの「会話の方向を逆転させる」原則に基づく対話パターン：

1. **AIが主導する** — 「次に何をしましょうか？」ではなく「次はペルソナを定義します。以下の3つのペルソナを提案しますが、調整が必要ですか？」
2. **具体的な提案を先に出す** — 空白のテンプレートを渡すのではなく、AIが埋めた案を提示して修正を求める
3. **判断はユーザーに委ねる** — 技術的・ビジネス的に重要な判断は、選択肢とトレードオフを提示してユーザーに決めてもらう
4. **段階的に進める** — 一度に全部を出さず、計画の各ステップを順に実行し、各ステップで承認を得る

---

## ありがちな失敗パターンと対策

- **ストーリーが大きすぎる** → ボルト（時間〜日単位）で完了可能か確認し、分割を提案
- **受け入れ基準が曖昧** → 「〜できること」ではなく具体的な検証可能条件にする
- **NFRが後回しになる** → ストーリー詳細化と並行してNFRも定義する
- **ドメイン用語が不統一** → DDDフレーバーの場合、ユビキタス言語の用語集を早期に作成
- **計画なしに実行開始** → 必ず計画ファイルを作成し承認を得てから進める
