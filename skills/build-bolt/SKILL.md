# AI-DLC build-bolt スキル

## このスキルの目的

AI-DLCの構築フェーズにおいて、1ボルトの全工程を1つの連続セッションで実行する。
旧 aidlc-design と aidlc-implementation を統合したスキル。

**設計原則:** スキルは「誰と、いつ話すか」を決める。エージェントは「何のコンテキストで
実行するか」を決める。開発者が1ボルトに着手してから完了するまでスキルを切り替える
理由がないため、設計から実装・検証まで1スキルに統合する。

## 前提知識

フレーバー別のドメイン設計手法は `references/domain-design-guide.md` を参照。
論理設計パターンとADRは `references/logical-design-guide.md` を参照。
ブラウンフィールドのモデル昇格は `references/brownfield-promotion.md` を参照。
コード生成パターンは `references/code-generation.md` を参照。
テスト戦略は `references/testing-strategy.md` を参照。

## 入力

**必須入力:**
- `aidlc-docs/handoffs/to_build.md` — ユニット一覧、ボルト計画、フレーバー
- `aidlc-docs/manifest.md` — 全成果物の台帳

**補助入力:**
- `aidlc-docs/story-artifacts/{ストーリーファイル}` — ストーリーと受け入れ基準
- `aidlc-docs/requirements/nfr_definition.md` — NFR定義
- `aidlc-docs/requirements/ubiquitous_language.md` — ユビキタス言語（DDDの場合）

入力が存在しない場合、aidlc:unit-decompositionスキルの先行実行を推奨する。

---

## ワークフロー

### step0: 入力読み込み・ボルト対象の決定

1. `manifest.md` を読み込む（なければ作成）
2. `handoffs/to_build.md` を読み込む
3. 作業対象のユニットとボルトを確認する（ユーザーに指定してもらう）
4. グリーンフィールドかブラウンフィールドかを確認する
5. フレーバー（DDD/BDD/TDD）を確認する

フォルダ構造を作成する（存在しない場合）:

```
aidlc-docs/design-artifacts/
├── domain-models/
├── logical-designs/
└── adrs/
```

### step1: ドメイン設計

AIがストーリーと受け入れ基準を分析し、ドメインモデルを提案する。
フレーバー別の詳細手法は `references/domain-design-guide.md` を参照。

**ブラウンフィールドの場合:** 既存コードの静的/動的モデル昇格から始める。
詳細は `references/brownfield-promotion.md` を参照。

**ドメインモデルの提案→承認→保存を一連の流れで行う:**
1. AIがコンポーネント一覧（全体像）を提案する
2. ユーザーがレビューし修正を指示する
3. 全体像が承認されたら、各コンポーネントの詳細を提案→承認する
4. **承認されたドメインモデルを即座にファイルに保存し、manifest.mdに登録する**

保存先: `aidlc-docs/design-artifacts/domain-models/{ユニット名}_domain_model.md`

**[承認ゲート]** ユーザーがドメインモデルを承認するまで次のステップに進まない。

### step2: 論理設計

ドメインモデル承認後、NFRとアーキテクチャパターンを適用する。
パターン選定の詳細は `references/logical-design-guide.md` を参照。

AIは以下を提案し、開発者が検証する:
1. **アーキテクチャパターンの選定** — NFRからパターンを推奨
2. **クラウドサービスの選定** — パターンに適したサービスをマッピング
3. **トレードオフの提示** — 各選択肢のメリット・デメリットを明示

**[承認ゲート]** 論理設計仕様をユーザーが承認するまで次のステップに進まない。

保存先: `aidlc-docs/design-artifacts/logical-designs/{ユニット名}_logical_design.md`

**ADRの作成:** 重要な決定を `aidlc-docs/design-artifacts/adrs/` 配下に記録。

**横断レビュー:** step2完了後、`aidlc:cross-review` エージェントを呼び出し、
設計整合性をチェックする。レビュー観点:
- STORY_DESIGN_ALIGN（ストーリーとドメインモデルの整合）
- NFR_PATTERN_ALIGN（NFRとパターン適用の整合）
- TERM_CONSISTENCY（用語の一貫性）

### step3: テスト契約

**テスト＝人間とAIの契約。** このステップが最も重要な承認ゲート。

`aidlc:test-generator` エージェントを呼び出し、テストコードを生成する。
エージェントへの入力:
- ドメインモデル
- 受け入れ基準（ストーリーファイル）
- フレーバー

生成されたテストをユーザーに提示し、以下の観点でレビューを依頼する:
- テストがビジネスロジックの正しい期待値を定義しているか
- テストケースの網羅性は十分か
- 受け入れ基準とテストの対応が正しいか

**[承認ゲート ※最重要]** ユーザーがテストを承認するまで実装に進まない。
テストへの修正要望があれば反映し、再度レビューを依頼する。

承認されたテストは「正しさの契約」として確定する。

### step4: ドメインレイヤー実装 (Red → Green → Refactor)

**Red:** 承認済みテストを実行し、全件が失敗することを確認する。

**Green:** `aidlc:code-generator` エージェントを呼び出し、テストを通す実装を生成する。
テストを実行して全件パスを確認。

**Refactor:** `aidlc:refactorer` エージェントを呼び出し、コード品質を改善する。
テストを実行してリグレッションがないことを確認。

**このステップでは人間の介入は原則不要。** テストが契約であり、
テストが通れば正しい。テストが落ちる改善はエージェントが自動ロールバックする。

### step5: インフラレイヤー実装

`aidlc:infra-impl` エージェントを呼び出し、インフラ実装と統合テストを生成する。

統合テストをユーザーに提示しレビューを依頼する。
**[承認ゲート]** 統合テストが承認されたら、Red → Green サイクルを実行。

### step6: 横断レビュー・最終検証

`aidlc:verification-report` エージェントを呼び出し、全テスト一括実行と検証レポートを生成。

`aidlc:cross-review` エージェントを呼び出し、コードと設計仕様の整合性を検証。
レビュー観点:
- CODE_MODEL_ALIGN（コードとドメインモデルの整合）
- AC_TEST_ALIGN（受け入れ基準とテストの1:1対応）
- ADR_IMPL_ALIGN（ADR決定と実装の整合）

結果をユーザーに提示。全成果物のステータスをmanifest.mdで最終確認。

**次のボルトがあればstep0に戻る。全ボルト完了後、handoffs/to_iac.md を生成。**

---

## 承認ゲートの一覧

| ステップ | 承認対象 | 重要度 | 承認者 |
|---------|---------|--------|-------|
| step1 | ドメインモデル | 高 | 開発者 |
| step2 | 論理設計・ADR | 高 | 開発者 |
| step3 | テストコード（＝正しさの契約） | **最高** | 開発者 |
| step4 | なし（テストが契約として機能） | — | — |
| step5 | 統合テスト | 中 | 開発者 |
| step6 | 検証レポート確認 | 中 | 開発者 |

---

## 対話スタイルのガイドライン

1. **図解を活用する** — ドメインモデルの関係やアーキテクチャ図をMermaid等で提示
2. **トレードオフを明示する** — 設計判断には必ず選択肢とトレードオフを提示
3. **テストを先に出す** — 実装コードの前にテストコードを提示し、人間のレビューを待つ
4. **Green後は簡潔に報告** — テストが全件パスしたら簡潔に報告

---

## ありがちな失敗パターンと対策

- **設計をスキップして実装に入る** → ワークフローの順序を厳守
- **テスト生成をスキップ** → テストが先。テスト承認は必須ゲート
- **モデルが技術に寄りすぎる** → ビジネス用語でモデル化し、技術は論理設計で扱う
- **NFRが設計に反映されない** → 論理設計で各NFRを明示的にパターンにマッピング
- **設計からの逸脱** → コード生成中にドメインモデルと論理設計を常に参照
