# AI-DLC build-bolt スキル

## トリガー条件

以下の場合にこのスキルを使用する：
- ユーザーが「ボルトの実装を開始」「設計から実装まで」「構築フェーズ」「モブ構築」「build-bolt」「ドメイン設計」「論理設計」「テスト生成」「コード生成」「実装」と言及した場合
- aidlc-unit-decomposition完了後に自然に続くフェーズ

## このスキルの目的

AI-DLCの構築フェーズにおいて、1ボルトの全工程を1つの連続セッションで実行する。
旧 aidlc-design と aidlc-implementation を統合したスキル。

**設計原則:** スキルは「誰と、いつ話すか」を決める。エージェントは「何のコンテキストで
実行するか」を決める。開発者が1ボルトに着手してから完了するまでスキルを切り替える
理由がないため、設計から実装・検証まで1スキルに統合する。

## 前提知識

フレーバー別のドメイン設計手法は `references/domain-design-guide.md` を参照。
論理設計パターンとADRは `references/logical-design-guide.md` を参照。
ブラウンフィールドのモデル昇格は `references/brownfield-promotion.md` を参照。
コード生成パターンは `references/code-generation.md` を参照。
テスト戦略は `references/testing-strategy.md` を参照。
並行実行の手順は `references/parallel-execution-guide.md` を参照。

## 入力

**必須入力:**
- `aidlc-docs/handoffs/to_build.md` — ユニット一覧、ボルト計画、フレーバー
- `aidlc-docs/manifest.md` — 全成果物の台帳

**補助入力:**
- `aidlc-docs/story-artifacts/{ストーリーファイル}` — ストーリーと受け入れ基準
- `aidlc-docs/requirements/nfr_definition.md` — NFR定義
- `aidlc-docs/requirements/ubiquitous_language.md` — ユビキタス言語（DDDの場合）

入力が存在しない場合、aidlc:unit-decompositionスキルの先行実行を推奨する。

## ワークフロー

### step0: 入力読み込み・ボルト対象の決定

1. `manifest.md` を読み込む（なければ作成）
2. `handoffs/to_build.md` を読み込む
3. 作業対象のユニットとボルトを確認する（ユーザーに指定してもらう）
4. グリーンフィールドかブラウンフィールドかを確認する
5. フレーバー（DDD/BDD/ストーリーベース）を確認する
6. **実行モードを確認する:**
   - **ボルト実行モード（デフォルト）** — 特定のボルトを設計・実装する
   - **完了モード** — 全ボルト完了後のファイナライズ（to_iac.md 生成）
7. **ボルト実行モードの場合:**
   a. `plans/bolt_schedule.md` を読み込み、選択ボルトの前提条件を検証する
      - 前提ボルトの成果物（verification_report）が統合ブランチの manifest.md に存在するか確認
      - 未充足の場合はユーザーに警告し、続行するか判断を仰ぐ
   b. 対象ボルト向けの延期ADRが存在するか確認する
      - `aidlc-docs/design-artifacts/adrs/` 配下のADRで「延期先ボルト」が現ボルトを指しているものを検索
      - 該当する延期ADRがあれば、step2（論理設計）で解決ADRの作成が必須であることを表示する
   b. git worktree を作成し、ボルト専用の作業ディレクトリを確保する:
      `git worktree add .worktrees/bolt-{ユニット名}-{ボルトID} -b bolt/{ユニット名}/{ボルトID}`
   c. 作業ディレクトリを worktree に移動する
   d. 以降の全ステップはこの worktree 上で実行する
8. **完了モードの場合:** → step6-final（完了モード処理）にジャンプする

フォルダ構造を作成する（存在しない場合）:

```
aidlc-docs/design-artifacts/
├── domain-models/
├── logical-designs/
└── adrs/
```

### 成果物IDの命名規則（並行実行対応）

manifest.md の成果物IDにボルト識別子を含めることで、並行セッション間での一意性を保証する:
- `DSG-B{ユニット番号}.{ボルト番号}-{連番}` （例: DSG-B1.1-001）
- `COD-B{ユニット番号}.{ボルト番号}-{連番}` （例: COD-B1.1-001）
- `RPT-B{ユニット番号}.{ボルト番号}-{連番}` （例: RPT-B1.1-001）
- `ADR-B{ユニット番号}.{ボルト番号}-{連番}` （例: ADR-B1.1-001）

### step1: ドメイン設計

AIがストーリーと受け入れ基準を分析し、ドメインモデルを提案する。
フレーバー別の詳細手法は `references/domain-design-guide.md` を参照。

**ブラウンフィールドの場合:** 既存コードの静的/動的モデル昇格から始める。
詳細は `references/brownfield-promotion.md` を参照。

**ドメインモデルの提案→承認→保存を一連の流れで行う:**
1. AIがコンポーネント一覧（全体像）を提案する
2. ユーザーがレビューし修正を指示する
3. 全体像が承認されたら、各コンポーネントの詳細を提案→承認する
4. **承認されたドメインモデルを即座にファイルに保存し、manifest.mdに登録する**

保存先: `aidlc-docs/design-artifacts/domain-models/{ユニット名}_domain_model.md`

**[承認ゲート]** ユーザーがドメインモデルを承認するまで次のステップに進まない。

**成果物登録・コミット:** ドメインモデルを manifest.md に登録し、prompts.md に記録してコミットする。
コミット: `aidlc(build-bolt): B{ボルトID} step1 ドメイン設計`

### step2: 論理設計

ドメインモデル承認後、NFRとアーキテクチャパターンを適用する。
パターン選定の詳細は `references/logical-design-guide.md` を参照。

AIは以下を提案し、開発者が検証する:
1. **アーキテクチャパターンの選定** — NFRからパターンを推奨
2. **クラウドサービスの選定** — パターンに適したサービスをマッピング
3. **トレードオフの提示** — 各選択肢のメリット・デメリットを明示

**[承認ゲート]** 論理設計仕様をユーザーが承認するまで次のステップに進まない。

保存先: `aidlc-docs/design-artifacts/logical-designs/{ユニット名}_logical_design.md`

**ADRの作成:** 重要な決定を `aidlc-docs/design-artifacts/adrs/` 配下に記録。

**ADRの延期:** 現ボルトで決定できない設計判断がある場合、ADRに「延期」セクションを追加する。
延期先ボルト（Bolt-X.Y）または「要計画」を明記し、延期理由とリスクを記録する。
詳細は `references/logical-design-guide.md` の「ADRの延期」セクションを参照。

**延期ADRの解決:** step0で延期ADRが検出された場合、以下の手順で解決する:
1. 延期元ADRを読み込み、延期されたコンテキストと選択肢を確認する
2. 現ボルトの論理設計の中で決定を行い、新しいADR（解決ADR）を作成する
3. 延期元ADRの「延期」セクションに以下を追記する:
   - `解決: ADR-B{X.Y}-{N} で決定済み`（解決ADRへの参照）
   - `延期先ボルト` フィールドの値を解決済みボルトIDに更新する
4. 解決ADRと更新した延期元ADRの両方をmanifest.mdに登録する

**横断レビュー:** step2完了後、`aidlc:cross-review` エージェントを呼び出し、
設計整合性をチェックする。レビュー観点:
- STORY_DESIGN_ALIGN（ストーリーとドメインモデルの整合）
- NFR_PATTERN_ALIGN（NFRとパターン適用の整合）
- TERM_CONSISTENCY（用語の一貫性）

**成果物登録・コミット:** 論理設計・ADR・レビュー結果を manifest.md に登録し、prompts.md に記録してコミットする。
コミット: `aidlc(build-bolt): B{ボルトID} step2 論理設計`

### step3: テスト契約

**テスト＝人間とAIの契約。** このステップが最も重要な承認ゲート。

`aidlc:test-generator` エージェントを呼び出し、テストコードを生成する。
エージェントへの入力:
- ドメインモデル
- 受け入れ基準（ストーリーファイル）
- フレーバー

生成されたテストをユーザーに提示し、以下の観点でレビューを依頼する:
- テストがビジネスロジックの正しい期待値を定義しているか
- テストケースの網羅性は十分か
- 受け入れ基準とテストの対応が正しいか

**[承認ゲート ※最重要]** ユーザーがテストを承認するまで実装に進まない。
テストへの修正要望があれば反映し、再度レビューを依頼する。

承認されたテストは「正しさの契約」として確定する。

**成果物登録・コミット:** テストコードを manifest.md に登録し、prompts.md に記録してコミットする。
コミット: `aidlc(build-bolt): B{ボルトID} step3 テスト契約`

### step4: ドメインレイヤー実装 (Red → Green → Refactor)

**Red:** 承認済みテストを実行し、全件が失敗することを確認する。

**Green:** `aidlc:code-generator` エージェントを呼び出し、テストを通す実装を生成する。
テストを実行して全件パスを確認。

**Refactor:** `aidlc:refactorer` エージェントを呼び出し、コード品質を改善する。
テストを実行してリグレッションがないことを確認。

**このステップでは人間の介入は原則不要。** テストが契約であり、
テストが通れば正しい。テストが落ちる改善はエージェントが自動ロールバックする。

**成果物登録・コミット:** 実装コードを manifest.md に登録し、prompts.md に記録してコミットする。
コミット: `aidlc(build-bolt): B{ボルトID} step4 ドメインレイヤー実装`

### step5: インフラレイヤー実装

`aidlc:infra-impl` エージェントを呼び出し、インフラ実装と統合テストを生成する。

統合テストをユーザーに提示しレビューを依頼する。
**[承認ゲート]** 統合テストが承認されたら、Red → Green サイクルを実行。

**成果物登録・コミット:** インフラ実装と統合テストを manifest.md に登録し、prompts.md に記録してコミットする。
コミット: `aidlc(build-bolt): B{ボルトID} step5 インフラレイヤー実装`

### step6: 横断レビュー・最終検証

`aidlc:verification-report` エージェントを呼び出し、全テスト一括実行と検証レポートを生成。

`aidlc:cross-review` エージェントを呼び出し、コードと設計仕様の整合性を検証。
レビュー観点:
- CODE_MODEL_ALIGN（コードとドメインモデルの整合）
- AC_TEST_ALIGN（受け入れ基準とテストの1:1対応）
- ADR_IMPL_ALIGN（ADR決定と実装の整合）

結果をユーザーに提示。

**成果物登録・コミット:** 検証レポート・レビュー結果を manifest.md に登録し、prompts.md に記録してコミットする。
コミット: `aidlc(build-bolt): B{ボルトID} step6 横断レビュー・最終検証`

**ボルト完了処理（ボルト実行モード）:**
1. manifest.md の自ボルト成果物のステータスを最終確認する（全エントリが登録済みであること）
2. 未コミットの変更があればコミットする
3. ユーザーにボルト完了を報告する
4. 統合ブランチへのPR作成を推奨する: `bolt/{ユニット名}/{ボルトID}` → 統合ブランチ
5. `bolt_schedule.md` に基づき、次に実行可能なボルトを提示する
6. 全ボルトが完了済みの場合、完了モードの実行を推奨する
7. worktree のクリーンアップはPRマージ後にユーザーが実施:
   `git worktree remove .worktrees/bolt-{ユニット名}-{ボルトID}`

### step6-final: 完了モード処理（全ボルト完了後）

完了モードは統合ブランチ上で直接実行する（worktreeは作成しない）。

1. `bolt_schedule.md` を読み込み、全ボルトの一覧を取得する
2. 各ボルトの `verification_report_{bolt}.md` が manifest.md に存在するか確認する
   - 不足がある場合、未完了ボルトを一覧表示して中断する
3. **全ADRの延期フィールドを確認する**
   - `aidlc-docs/design-artifacts/adrs/` 配下の全ADRを走査し、「延期先ボルト」フィールドを検査する
   - 「要計画」が残っている → 未解決ADRを一覧表示して**中断する**
   - 延期先ボルトが指定されているが、そのボルトで解決ADRが作成されていない → 警告を表示する
4. 全 `bolt/` ブランチが統合ブランチにマージ済みか確認する
   - 未マージがある場合、未マージブランチを一覧表示して中断する
5. 統合ブランチ上で全テストを一括実行する
6. **E2E ブラウザ検証（UIプロジェクトの場合）**
   - `bolt_schedule.md` の「プレゼンテーション層チェック結果」を参照する
   - **UIプロジェクト（UIの有無: はい）の場合:**
     a. アプリケーションをローカルで起動する
     b. 各ストーリーの受け入れ基準に対応するユーザーシナリオをブラウザで手動検証する
     c. 検証結果を `aidlc-docs/reports/e2e_verification_report.md` に記録する
     d. 全シナリオの検証完了をユーザーに確認する
     e. NGがある場合、修正ボルトの追加が必要かユーザーと判断する
   - **非UIプロジェクト（UIの有無: いいえ）の場合:** スキップ
   - E2E検証レポートのフォーマット:
     ```markdown
     # E2E ブラウザ検証レポート

     ## 検証環境
     - ブラウザ: {Chrome / Firefox / etc}
     - 画面サイズ: {desktop / mobile}
     - ローカルURL: {http://localhost:XXXX}

     ## シナリオ検証結果
     | # | ストーリー | シナリオ | 検証結果 | 備考 |
     |---|-----------|---------|---------|------|
     | 1 | US-001 | {シナリオ概要} | {OK / NG} | {NGの場合の詳細} |

     ## 自動テストとの整合
     - ユニットテスト: 全件パス
     - 統合テスト: 全件パス
     - E2E手動検証: {全件OK / NG件数}

     ## 判定
     {全件OK → 完了可能 / NG あり → 修正ボルトが必要}
     ```
7. `aidlc:cross-review` エージェントを全ユニット横断で実行する
   レビュー観点: CODE_MODEL_ALIGN, AC_TEST_ALIGN, ADR_IMPL_ALIGN, ADR_DEFERRAL_RESOLVED
8. `aidlc:handoff-generator` エージェントで `handoffs/to_iac.md` を生成する
9. ユーザーに完了報告と次フェーズ（aidlc:iac）の開始を提示する

## 成果物の記録・コミット規約

各承認ゲート通過時・ステップ完了時に、以下を一連の流れで実行する:
1. **prompts.md 記録** — 実行内容の要約を `aidlc-docs/prompts.md` に追記する
2. **manifest.md 登録** — 保存したファイルを `aidlc-docs/manifest.md` に登録する（存在しなければ作成）
3. **コミット** — 成果物ファイル + manifest.md + prompts.md をまとめてコミットする

コミットメッセージ規約: `aidlc(build-bolt): B{ボルトID} step{N} {概要}`

prompts.md のフォーマット:
```markdown
## step{N}: {ステップ名} — {タイムスタンプ}
- ボルト: B{ボルトID}
- 指示: {実行内容の要約}
- ユーザー判断: {ユーザーが行った主要な決定}
- 結果: {生成された成果物のファイルパス}
```

## 承認ゲートの一覧

| ステップ | 承認対象 | 重要度 | 承認者 |
|---------|---------|--------|-------|
| step1 | ドメインモデル | 高 | 開発者 |
| step2 | 論理設計・ADR | 高 | 開発者 |
| step3 | テストコード（＝正しさの契約） | **最高** | 開発者 |
| step4 | なし（テストが契約として機能） | — | — |
| step5 | 統合テスト | 中 | 開発者 |
| step6 | 検証レポート確認 | 中 | 開発者 |

## 対話スタイルのガイドライン

1. **図解を活用する** — ドメインモデルの関係やアーキテクチャ図をMermaid等で提示
2. **トレードオフを明示する** — 設計判断には必ず選択肢とトレードオフを提示
3. **テストを先に出す** — 実装コードの前にテストコードを提示し、人間のレビューを待つ
4. **Green後は簡潔に報告** — テストが全件パスしたら簡潔に報告

## ありがちな失敗パターンと対策

- **設計をスキップして実装に入る** → ワークフローの順序を厳守
- **テスト生成をスキップ** → テストが先。テスト承認は必須ゲート
- **モデルが技術に寄りすぎる** → ビジネス用語でモデル化し、技術は論理設計で扱う
- **NFRが設計に反映されない** → 論理設計で各NFRを明示的にパターンにマッピング
- **設計からの逸脱** → コード生成中にドメインモデルと論理設計を常に参照
