# 論理設計ガイド

## 論理設計とは

論理設計は、ドメイン設計（ビジネスロジックの純粋なモデル）を拡張し、
非機能要件（NFR）を満たすためにアーキテクチャパターンと技術選定を適用する。
ドメイン設計が「何を作るか」なら、論理設計は「どう作るか」を定義する。

---

## NFR分析の進め方

1. ユニットに関連するNFR IDを `nfr_definition.md` から抽出
2. 各NFRがドメイン設計のどのコンポーネントに影響するか分析
3. NFRの優先度と制約の厳しさを評価

**NFR影響分析テーブル：**
```markdown
| NFR ID | 影響を受けるコンポーネント | 設計への影響 | 対応パターン候補 |
|--------|------------------------|-------------|----------------|
| NFR-P01 | {コンポーネント名} | {レスポンスタイム制約} | キャッシュ, 非同期処理 |
```

## よく使うアーキテクチャパターン

AIがパターンを推奨する際は、以下から適切なものを選び、
必ず複数の選択肢とトレードオフを開発者に提示する。

### データ管理パターン
- **CQRS（Command Query Responsibility Segregation）** — 読み取りと書き込みの最適化が異なる場合。読み取りヘビーなシステムに有効。コスト: 複雑性の増加
- **イベントソーシング** — 状態変更の完全な履歴が必要な場合。監査要件に有効。コスト: クエリの複雑化
- **データベースperサービス** — マイクロサービス間のデータ独立性。コスト: 結合クエリの困難さ

### 通信パターン
- **イベント駆動** — サービス間の疎結合な非同期通信。コスト: デバッグの複雑さ
- **API Gateway** — 外部クライアントへの統一エンドポイント。コスト: 単一障害点のリスク
- **サーキットブレーカー** — 外部サービス障害時のカスケード防止。コスト: 実装の複雑さ

### 信頼性パターン
- **リトライ + 指数バックオフ** — 一時的な障害への対処
- **デッドレターキュー** — 処理不能メッセージの隔離
- **バルクヘッド** — 障害の影響範囲の制限

### スケーリングパターン
- **水平スケーリング** — ステートレスなサービスの複製
- **キャッシュ戦略**（ライトスルー/ライトバック/キャッシュアサイド）
- **非同期処理 + キュー** — ピーク負荷の平準化

## ADR（Architecture Decision Record）

### いつADRを作成するか

以下の判断にはADRを作成する：
- アーキテクチャパターンの選定（例: CQRS vs 単純なCRUD）
- データストアの選定（例: DynamoDB vs Aurora PostgreSQL）
- 通信方式の選定（例: 同期REST vs 非同期イベント）
- フレームワーク/言語の選定
- セキュリティモデルの選定

逆に、以下にはADRは不要：
- 変数名やコーディングスタイルの決定
- ライブラリのマイナーバージョン選択
- 自明なパターン適用

### ADRの書き方のコツ

- **コンテキストは具体的に** — 「パフォーマンスが重要」ではなく「P95で300ms以内の応答が必要」
- **選択肢は最低2つ** — 1つしか選択肢がないなら決定ではない
- **棄却した理由も記録** — 将来再検討する際に同じ議論を繰り返さない
- **影響を明確に** — この決定で何が変わるか、何がトレードオフになるか

## 論理設計仕様の品質チェック

論理設計仕様が以下を満たしているか確認する：

- [ ] すべての関連NFRに対応方法が定義されている
- [ ] 各コンポーネントの技術選定が明記されている
- [ ] コンポーネント間の通信方式が定義されている
- [ ] データ設計（データストア、スキーマの方針）が含まれている
- [ ] 重要な設計判断にADRが紐づいている
- [ ] 統合仕様（他ユニットとのインターフェース）との整合性がある
- [ ] セキュリティ要件への対応が含まれている
