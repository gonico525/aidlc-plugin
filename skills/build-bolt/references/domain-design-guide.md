# フレーバー別ドメイン設計ガイド

## DDDフレーバー（ドメイン駆動設計）

### 設計の進め方

1. **集約（Aggregate）の特定** — トランザクション整合性の境界を定義する。ストーリーの受け入れ基準から「一緒に変更される必要があるデータ群」を見つける
2. **エンティティと値オブジェクトの分類** — 識別子を持つ（ライフサイクルがある）ものはエンティティ、属性の組み合わせとして等価比較されるものは値オブジェクト
3. **ドメインイベントの特定** — ストーリーの受け入れ基準から「〜が発生したとき」のパターンを探す
4. **リポジトリの定義** — 各集約ルートに対するリポジトリインターフェース
5. **ドメインサービスの特定** — 単一の集約に収まらないビジネスロジック
6. **ファクトリの特定** — 複雑な生成ロジックがある場合

### DDDドメイン設計のフォーマット

```markdown
# ドメイン設計: {ユニット名}

## 集約

### {集約名}（集約ルート: {ルートエンティティ名}）

**不変条件:**
- {この集約が常に保証するビジネスルール}

**エンティティ:**
- {エンティティ名}: {属性一覧} — {責任}

**値オブジェクト:**
- {値オブジェクト名}: {属性一覧} — {意味}

**振る舞い:**
- {メソッド名}({引数}): {戻り値} — {ビジネスルール}

**ドメインイベント:**
- {イベント名}: {発生条件} — {ペイロード}

## リポジトリ
- {リポジトリ名}: {主要な操作（findById, save, findBy...等）}

## ドメインサービス
- {サービス名}: {責任} — {どの集約を跨ぐか}

## ファクトリ
- {ファクトリ名}: {生成対象} — {生成ロジックの概要}
```

### 設計の判断基準

- 集約は小さく保つ（エンティティ3つ以内が目安）
- 集約間の参照はIDのみ（直接のオブジェクト参照を避ける）
- 結果整合性（Eventual Consistency）を積極的に活用
- ユビキタス言語の用語をそのままクラス名・メソッド名に使う

## BDDフレーバー（振る舞い駆動開発）

### 設計の進め方

1. **フィーチャーの特定** — ユーザーストーリーの受け入れ基準（Given-When-Then）をフィーチャーとして整理
2. **振る舞いの抽出** — 各シナリオのWhen節から、システムが提供すべき操作を抽出
3. **コンポーネントへのマッピング** — 操作を担当するコンポーネントを定義
4. **コラボレーション設計** — シナリオのステップ順にコンポーネント間の連携を設計
5. **テスタビリティの確認** — 各コンポーネントがGiven-When-Thenで独立テスト可能か確認

### BDDドメイン設計のフォーマット

```markdown
# ドメイン設計: {ユニット名}

## フィーチャーマップ
| フィーチャー | 関連シナリオ数 | 主要コンポーネント |
|------------|--------------|------------------|
| {フィーチャー名} | {N} | {コンポーネントA, B} |

## コンポーネントモデル

### {コンポーネント名}
- 責任: {振る舞いの要約}
- 振る舞い:
  - {操作名}: シナリオ「{シナリオ名}」のWhen節に対応
- テスト可能性: {どうテストするか}

## シナリオ実現マップ
### シナリオ: {シナリオ名}
1. Given: {コンポーネントA}が{状態}
2. When: {コンポーネントB}.{操作}({引数})
3. Then: {コンポーネントC}が{期待結果}
```

## ストーリーベースフレーバー（軽量設計）

### 設計の進め方

1. **コンポーネントの特定** — ストーリーの受け入れ基準から必要な機能コンポーネントを特定する
2. **責任の定義** — 各コンポーネントの責任を1〜2文で記述する
3. **パブリックインターフェースの設計** — 受け入れ基準から逆算して必要なメソッドシグネチャを定義
4. **依存関係の整理** — コンポーネント間の依存関係と外部依存を明確にする
5. **テスト可能性の確認** — 各コンポーネントが独立してテスト可能か確認

### ストーリーベースドメイン設計のフォーマット

```markdown
# ドメイン設計: {ユニット名}

## コンポーネントモデル

### {コンポーネント名}
- 責任: {このコンポーネントが担う役割を1〜2文で}
- パブリックインターフェース:
  - {メソッドシグネチャ}: {振る舞いの概要}
- 依存:
  - {依存先コンポーネント名}: {依存の理由}
- テスト方針: {どうテストするか}

## コンポーネント間の依存関係
{コンポーネント間の依存関係を箇条書きまたは図で表現}
```

### 設計の判断基準

- DDD戦術パターン（集約・値オブジェクト等）は不要
- BDDフィーチャーマップも不要
- コンポーネントは受け入れ基準を満たすための最小単位
- 外部依存はインターフェースとして抽象化し、テスト時にモック差し替え可能にする
