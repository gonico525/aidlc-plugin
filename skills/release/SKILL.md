# AI-DLC リリーススキル

## トリガー条件

以下の場合にこのスキルを使用する：
- ユーザーが「リリース」「デプロイ」「本番環境」「パイプライン構築」「CI/CD」「環境構築」「ステージング」「運用準備」「モニタリング設定」「アラーム設定」「ランブック」と言及した場合
- aidlc-build-boltスキルで全ボルトが完了した後に自然に続くフェーズ
- コード生成やテストは別スキル（aidlc-build-bolt）の範囲

## このスキルの目的

AI-DLCにおいて、構築フェーズで生成されたテスト済みコード＋IaCを
**本番環境にリリース可能な状態**にするまでの全工程を支援する。

既存の4スキルが「ボルト単位のイテレーション」を支援するのに対し、
このスキルは**ユニット単位（または複数ユニット統合）のリリース**を支援する。
AI-DLCの構築フェーズの最終段階であり、運用フェーズへの橋渡しとして機能する。

## 前提知識

クラウドプロバイダー固有のデプロイメント手法とサービスは参照ファイルを確認する。
対象プロバイダーに応じて以下を読み込む：
- AWS: `references/aws-deployment.md`
- GCP: `references/gcp-deployment.md`（将来追加）
- Azure: `references/azure-deployment.md`（将来追加）

## 入力

**必須入力：**
- `aidlc-docs/handoffs/to_release.md` — デプロイメントユニット情報、SLA基準
- `aidlc-docs/design-artifacts/logical-designs/{ユニット名}_logical_design.md` — サービスマッピング、通信設計、セキュリティ設計
- `aidlc-docs/reports/verification_report_{ボルト名}.md` — 全ボルトのテスト結果（全件パス確認済み）
- 生成済みの実装コードとIaCコード（aidlc:build-boltが出力したプロジェクトフォルダ）

**補助入力：**
- `aidlc-docs/design-artifacts/adrs/` — アーキテクチャ決定記録
- `aidlc-docs/design-artifacts/integration_specs.md` — ユニット間統合仕様
- `aidlc-docs/requirements/nfr_definition.md` — 可用性、パフォーマンスのSLA基準
- `aidlc-docs/requirements/risk_description.md` — 運用リスクとその緩和策
- `aidlc-docs/requirements/business_metrics.md` — ビジネスKPI（モニタリングダッシュボードに反映）
- `aidlc-docs/handoffs/to_build.md` — 開発種別（グリーン/ブラウンフィールド）

**前提条件：**
- 対象ユニットの全ボルトが完了し、全テストがパスしていること
- IaCコードが生成済みであること
- クラウドプロバイダーのアカウント/プロジェクトが利用可能であること

## ワークフロー

### ステップ0：入力の読み込みと前提確認

1. 全ボルトの検証レポートを読み込み、全テストパスを確認する
2. 論理設計仕様からクラウドプロバイダーとサービス構成を特定する
3. プロバイダーに応じた参照ファイル（`references/{provider}-deployment.md`）を読み込む
4. NFR定義から可用性・パフォーマンスのSLA基準を確認する
5. ブラウンフィールドの場合、既存環境との共存方法を確認する

**前提条件が満たされていない場合（テスト未完了、IaC未生成等）は、先行スキルの完了を促す。**

### ステップ1：リリース計画の作成

`aidlc-docs/plans/release_plan_{ユニット名}.md` に保存する。

```markdown
# リリース計画: {ユニット名}

## 前提確認
- 全ボルトのテスト結果: {全件パス確認}
- クラウドプロバイダー: {AWS / GCP / Azure}
- 開発種別: {グリーンフィールド / ブラウンフィールド}

## 計画ステップ
- [ ] 1. 環境戦略の定義
- [ ] 2. CI/CDパイプラインの設計と構築
- [ ] 3. ステージング環境へのデプロイ
- [ ] 4. ステージングでのスモークテスト
- [ ] 5. 観測可能性の設定（メトリクス、ログ、トレース、アラーム）
- [ ] 6. 運用ドキュメント（ランブック）の作成
- [ ] 7. 本番デプロイの承認と実行
- [ ] 8. 本番スモークテストと検証

## 確認事項
{ユーザーに確認が必要な判断事項}
```

**計画はユーザーの承認を得てから実行する。**

### ステップ2：環境戦略の定義

デプロイ先の環境構成を定義する。

`aidlc-docs/design-artifacts/environment_strategy.md` に保存：

```markdown
# 環境戦略: {ユニット名}

## 環境一覧
| 環境 | 用途 | アカウント/プロジェクト | 備考 |
|------|------|----------------------|------|
| dev | 開発・デバッグ | {ID} | 自動デプロイ |
| staging | 統合テスト・受け入れ | {ID} | 本番同等構成 |
| prod | 本番 | {ID} | 承認ゲート付き |

## 環境間の差異
| 設定項目 | dev | staging | prod |
|---------|-----|---------|------|
| インスタンスサイズ/同時実行数 | 最小 | 本番同等 | 本番スペック |
| データ | テストデータ | 匿名化本番データ | 本番データ |
| ドメイン | {dev用} | {staging用} | {本番用} |

## シークレット管理
{シークレットストア（Secrets Manager等）の利用方針}

## ネットワーク構成
{VPC/サブネット/セキュリティグループの設計（プロバイダー固有の詳細は参照ファイル）}
```

環境戦略はユーザーに確認する。既存の環境がある場合はそれに合わせる。

### ステップ3：CI/CDパイプラインの設計と構築

論理設計のサービス構成と環境戦略に基づいて、CI/CDパイプラインを設計・生成する。
プロバイダー固有のサービスは参照ファイルを確認。

**パイプラインの共通構成：**

```
[ソース] → [ビルド] → [テスト] → [ステージングデプロイ] → [スモークテスト] → [承認ゲート] → [本番デプロイ]
```

AIは以下を生成する：
- パイプライン定義ファイル（プロバイダー固有の形式）
- ビルドスクリプト（依存解決、パッケージ化）
- テスト実行スクリプト（aidlc:build-boltで作成したテストの自動実行）
- デプロイスクリプト（IaCの実行）
- スモークテストスクリプト（デプロイ後の疎通確認）

**マルチユニットの場合：**
複数ユニットが統合仕様で接続される場合、統合デプロイの順序を
`integration_specs.md`の依存関係に基づいて決定する。

### ステップ4：ステージングデプロイとスモークテスト

AIがステージング環境へのデプロイ手順を提示し、ユーザーが実行を承認する。

**スモークテストの内容：**
- API疎通確認（ヘルスチェックエンドポイント）
- 主要ユースケースの正常系1パス
- 外部連携の疎通（ユニット間API、外部サービス）
- データストアの接続確認

スモークテストはAIが生成し、パイプライン内で自動実行される。
失敗した場合はAIが原因を分析し、修正案を提示する。

### ステップ5：観測可能性の設定

NFR定義とビジネス測定基準に基づき、モニタリング構成を設計・生成する。

**3つの柱：**

1. **メトリクス** — NFRのSLA基準をダッシュボードとアラームに変換
2. **ログ** — 構造化ログの設定、ログレベルの定義、保持期間
3. **トレース** — 分散トレーシングの設定（ユニット間の呼び出しチェーン）

`aidlc-docs/design-artifacts/observability_config.md` に保存：

```markdown
# 観測可能性設定: {ユニット名}

## ダッシュボード
| パネル名 | メトリクス | ソース | 対応NFR |
|---------|----------|--------|---------|
| {名前} | {メトリクス名} | {サービス} | {NFR-ID} |

## アラーム
| アラーム名 | 条件 | 閾値 | アクション | 対応NFR |
|-----------|------|------|----------|---------|
| {名前} | {メトリクス} {演算子} {閾値} | {期間} | {通知先} | {NFR-ID} |

## ログ設計
| コンポーネント | ログレベル | 構造化フィールド | 保持期間 |
|--------------|----------|----------------|---------|

## トレース設計
| トレース対象 | 計装方法 | サンプリング率 |
|-------------|---------|-------------|
```

### ステップ6：運用ドキュメントの作成

AIがランブックと運用手順書を生成する。

`aidlc-docs/operations/runbook_{ユニット名}.md` に保存：

```markdown
# ランブック: {ユニット名}

## システム概要
{アーキテクチャの簡潔な説明と主要コンポーネント}

## 正常時の運用
| 作業 | 頻度 | 手順 | 自動化状況 |
|------|------|------|-----------|

## インシデント対応
### {アラーム名}: {症状}
**影響:** {ユーザーへの影響}
**原因候補:** {よくある原因のリスト}
**対応手順:**
1. {手順1}
2. {手順2}
**エスカレーション:** {次の対応者/チーム}

## ロールバック手順
{デプロイメントを前バージョンに戻す手順}

## 連絡先
| 役割 | 担当 | 連絡方法 |
|------|------|---------|
```

リスク説明の各運用リスクに対応するインシデント対応手順を含める。

### ステップ7：本番デプロイ

**ユーザーの明示的な承認を得てから本番デプロイを実行する。**

承認の判断材料として以下を提示する：
- ステージングでの全テスト結果
- スモークテスト結果
- 観測可能性の設定完了状況
- ランブックの準備状況
- ロールバック手順の確認

デプロイ戦略はユーザーと合意する（参照ファイルに選択肢を記載）：
- **ローリングデプロイ** — 段階的に置換
- **ブルー/グリーン** — 環境を切り替え
- **カナリア** — 少量のトラフィックから段階的に

### ステップ8：本番検証と完了

本番デプロイ後、以下を確認する：
- スモークテストの本番実行
- メトリクスとアラームの動作確認
- ログとトレースの出力確認

`aidlc-docs/reports/release_report_{ユニット名}.md` に保存：

```markdown
# リリースレポート: {ユニット名}

## リリース情報
| 項目 | 値 |
|------|-----|
| リリース日時 | {日時} |
| デプロイ戦略 | {ローリング/ブルーグリーン/カナリア} |
| 対象環境 | {prod} |

## 検証結果
| 検証項目 | 結果 |
|---------|------|
| ステージングテスト | {パス/フェイル} |
| 本番スモークテスト | {パス/フェイル} |
| メトリクス確認 | {正常/異常} |
| アラーム動作確認 | {正常/異常} |

## 運用準備状況
| 項目 | 状況 |
|------|------|
| ダッシュボード | {設定済み/未設定} |
| アラーム | {設定済み/未設定} |
| ランブック | {作成済み/未作成} |
| ロールバック手順 | {確認済み/未確認} |
```

prompts.mdにも各ステップの実行記録を追記する。
フォーマットはaidlc-user-storiesスキルで定義された形式に従う。

## 対話スタイルのガイドライン

1. **承認ゲートを厳守する** — 本番デプロイは必ずユーザーの明示的承認を得る。ステージングの結果を判断材料として提示する
2. **環境差異を明確にする** — dev/staging/prodの違いを常に意識し、環境固有の設定を混同しない
3. **ロールバックを常に準備** — デプロイ前にロールバック手順を確認し、問題発生時に即座に戻せる状態を維持する
4. **運用者の視点で書く** — ランブックやアラームは、深夜にオンコールで起こされた人が読んで対応できるレベルの具体性で書く

---

## ありがちな失敗パターンと対策

- **テスト未完了でデプロイ** → 全ボルトの検証レポートを前提条件チェック
- **環境間の設定差異** → 環境変数とシークレットを環境戦略で一元管理
- **ロールバック手順の未整備** → デプロイ前にロールバック手順をランブックに記載・確認
- **アラームの閾値が不適切** → NFR定義のSLA基準から機械的に導出
- **ランブックが抽象的** → 具体的なコマンド・手順を記載し、コピペで実行可能に
- **マルチユニット統合の順序ミス** → 統合仕様の依存関係に基づいてデプロイ順を決定
