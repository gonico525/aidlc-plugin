# 運用ガイド

## テレメトリ分析の基本

### 3つの柱

| 柱 | 目的 | 代表的なツール |
|----|------|--------------|
| **メトリクス** | 数値的な健全性の把握 | CloudWatch Metrics, Prometheus, Datadog |
| **ログ** | イベントの詳細な記録と検索 | CloudWatch Logs, ELK Stack, Splunk |
| **トレース** | リクエストの横断的な追跡 | X-Ray, Jaeger, Zipkin |

### メトリクス分析のポイント

- **ベースラインの確立** — 正常時のメトリクス範囲を把握する（1週間以上のデータ）
- **トレンド検出** — 緩やかな劣化（メモリリーク、ディスク増加等）を早期に発見
- **相関分析** — 複数メトリクスの同時変動パターンから根本原因を推定
- **USE法** — 各リソースについて Utilization（使用率）、Saturation（飽和度）、Errors（エラー率）を確認

### ログ分析のポイント

- **構造化ログ** — JSON形式で出力し、フィールド単位の検索・集計を可能にする
- **相関ID** — リクエストID/トレースIDでログを横断検索する
- **エラーの分類** — 一時的エラー（リトライで解消）と永続的エラー（修正が必要）を区別
- **ログレベルの運用** — 本番は `WARN` 以上、調査時に動的に `DEBUG` に切り替え可能にする

## インシデント対応フレームワーク

### 重大度分類

| 重大度 | 定義 | 応答時間 | エスカレーション |
|--------|------|---------|----------------|
| **P1** | サービス全停止、データ損失のリスク | 15分以内 | 即時、全関係者に通知 |
| **P2** | 主要機能の障害、多数ユーザーに影響 | 30分以内 | チームリード + SRE |
| **P3** | 一部機能の劣化、少数ユーザーに影響 | 2時間以内 | 担当エンジニア |
| **P4** | 軽微な問題、ワークアラウンドあり | 次営業日 | バックログに登録 |

### インシデント対応フロー

```
検知 → トリアージ → 初期対応 → 根本原因調査 → 恒久対策 → ポストモーテム
```

1. **検知** — アラーム発報、ユーザー報告、メトリクス異常
2. **トリアージ** — 重大度を判定し、応答チームを決定
3. **初期対応** — 影響範囲の限定（ロールバック、トラフィック制御等）
4. **根本原因調査** — テレメトリデータから原因を特定
5. **恒久対策** — コード修正、設定変更、アーキテクチャ改善
6. **ポストモーテム** — 振り返りと再発防止策の策定

### インシデント対応のアンチパターン

- **推測で対応する** → 必ずデータ（メトリクス/ログ/トレース）に基づいて判断
- **複数の変更を同時に行う** → 1つずつ変更し、効果を確認してから次に進む
- **ロールバックを躊躇する** → 原因が不明な場合はまずロールバックして安定化

## 継続的改善

### 週次運用レビュー

毎週以下を確認し、改善アクションを特定する：

- SLA達成状況（稼働率、レスポンスタイム、エラー率）
- アラーム発報履歴（ノイジーアラームの特定）
- インシデント発生件数と対応時間のトレンド
- リソース使用率のトレンド（キャパシティプランニング）

### ブレームレス・ポストモーテム

- **目的は学習であり、犯人探しではない**
- タイムラインの記録（検知→対応→解決の各タイムスタンプ）
- 何がうまくいったか / 何が改善できるか
- 具体的なアクションアイテム（担当者と期限付き）

### アラームチューニング

| 問題 | 対策 |
|------|------|
| 誤報が多い（ノイジー） | 閾値の緩和、評価期間の延長、複合条件の導入 |
| 検知が遅い | 閾値の引き下げ、異常検知アルゴリズムの導入 |
| アラーム疲れ | 重大度別のルーティング、自動復旧の導入 |
| 根本原因と紐づかない | 原因ベースのアラーム設計（症状だけでなく原因を監視） |
