# モックアップ設計ガイド

## フィデリティレベル

モックアップの詳細度は3段階。プロジェクトのフェーズと目的に応じて選択する。

### ワイヤーフレーム（Low Fidelity）

**目的：** 画面構造とレイアウトの合意。「何がどこにあるか」を定義する。
**適用場面：** 初期のステークホルダーデモ、画面一覧の確認、チーム内の構造合意。

**生成ルール：**
- グレースケールのみ（色は使わない）
- ボックスとラベルで要素を表現
- 実際のテキストではなくプレースホルダー（ただし要素名は正確に）
- インタラクションは最小限（画面遷移のリンクのみ）
- フォントは1種類のみ

```html
<!-- ワイヤーフレームのスタイル例 -->
<style>
  * { font-family: system-ui, sans-serif; }
  .placeholder { background: #e0e0e0; border: 1px solid #999; padding: 12px; }
  .text-placeholder { background: #ccc; height: 1em; border-radius: 2px; }
  .button-placeholder { background: #999; color: white; padding: 8px 16px; }
</style>
```

### ミッドフィデリティ（Mid Fidelity）

**目的：** レイアウト＋基本的なビジュアルスタイルの合意。「どう見えるか」の方向性を定義する。
**適用場面：** UI/UXの認識合わせ、主要フローの検証、フロントエンド設計の方向性確認。

**生成ルール：**
- ブランドカラーの基本パレットを適用（2〜3色）
- 実際のテキストとリアルなダミーデータを使用
- 基本的なタイポグラフィ階層（見出し、本文、キャプション）
- 主要なインタラクション（ボタンクリック、フォーム入力、タブ切り替え）を動作させる
- アイコンはシンプルなもの（lucide-react等）を使用

### ハイフィデリティ（High Fidelity）

**目的：** 完成形に近いビジュアルデザイン。「実際にこう見える」を体験させる。
**適用場面：** ステークホルダーの最終承認、フロントエンド実装の足場、ユーザビリティテスト。

**生成ルール：**
- 完全なカラーパレット、タイポグラフィ、スペーシング
- リアルなダミーデータ（実際のユースケースを想起できるもの）
- マイクロインタラクション（ホバー、トランジション、アニメーション）
- レスポンシブ対応（指定デバイスに応じて）
- アクセシビリティ対応（色コントラスト、フォーカス管理、ARIA属性）
- エッジケース画面（0件表示、エラー状態、ローディング状態）

## 画面種別のパターン

### 一覧画面（List / Table）

```markdown
構成要素：
- ヘッダー（タイトル、アクションボタン）
- フィルター/検索バー
- データテーブルまたはカードリスト
- ページネーション
- 空状態メッセージ（データ0件時）

受け入れ基準との対応：
- 「一覧が表示される」→ テーブル/カード
- 「検索できる」→ 検索バー
- 「ソートできる」→ カラムヘッダーのソートアイコン
- 「フィルタできる」→ フィルターコンポーネント
```

### 詳細画面（Detail）

```markdown
構成要素：
- ヘッダー（タイトル、戻るボタン、編集ボタン）
- メイン情報セクション
- 関連情報セクション（タブまたはアコーディオン）
- アクションバー（操作ボタン群）

受け入れ基準との対応：
- 「詳細が表示される」→ メイン情報セクション
- 「関連する〜が表示される」→ 関連情報セクション
- 「〜できる」→ アクションボタン
```

### フォーム画面（Form / Input）

```markdown
構成要素：
- フォームタイトル
- 入力フィールド群（ラベル、入力、バリデーションメッセージ）
- アクションボタン（保存、キャンセル）
- 確認ダイアログ（必要に応じて）

受け入れ基準との対応：
- 「〜を入力できる」→ 入力フィールド
- 「〜を選択できる」→ セレクト/ラジオ/チェックボックス
- 「〜を設定できる」→ トグル/スライダー
- バリデーションルール → エラーメッセージのデザイン
```

### ダッシュボード画面（Dashboard）

```markdown
構成要素：
- KPIカード群（主要指標の数値表示）
- グラフ/チャート（トレンド、比較）
- フィルター（期間、カテゴリ）
- アラート/通知セクション

受け入れ基準との対応：
- 「〜率が表示される」→ KPIカード
- 「〜が集計される」→ グラフ/テーブル
- 「期間で絞り込める」→ 期間フィルター
- business_metrics.mdのKPI → ダッシュボードのパネル設計
```

## ダミーデータのガイドライン

モックアップのダミーデータは**リアルさ**が重要。
抽象的なプレースホルダーは避け、実際のユースケースを想起できるデータにする。

**良いダミーデータ：**
- 商品名: 「オーガニック玄米 5kg」「ワイヤレスイヤホン Pro Max」
- ユーザー名: 「田中 美咲」「佐藤 健太」
- 日付: 具体的な日付（2026-03-15）
- 金額: 現実的な金額（¥2,980、¥12,500）
- 件数: 現実的な件数（レコメンデーション: 5件、注文: 127件）

**悪いダミーデータ：**
- 「テスト商品1」「サンプルユーザー」「XXX円」
- すべて同じ値の繰り返し
- 非現実的な値（商品100万件、価格0円）

## 受け入れ基準から画面要素への変換ルール

ストーリーの受け入れ基準を画面要素に変換する際の考え方：

| 受け入れ基準のパターン | 画面要素 |
|---------------------|---------|
| 「〜が表示される」 | テキスト、ラベル、データ表示領域 |
| 「〜の一覧が表示される」 | テーブル、カードリスト |
| 「〜を入力できる」 | テキストフィールド、テキストエリア |
| 「〜を選択できる」 | セレクトボックス、ラジオボタン、チェックボックス |
| 「〜をクリックすると」 | ボタン、リンク |
| 「〜が通知される」 | トースト、バナー、バッジ |
| 「〜でソートできる」 | テーブルヘッダーのソートコントロール |
| 「〜でフィルタできる」 | フィルターバー、検索ボックス |
| 「〜がN件以内であること」 | ページネーション、件数表示 |
| 「〜の場合、エラーが表示される」 | エラーメッセージ、バリデーション表示 |
| 「〜が無い場合」 | 空状態画面（Empty State） |
| 「〜が障害の場合」 | エラー画面、フォールバック表示 |

BDDフレーバーのGiven-When-Thenからの変換：
- **Given** → 画面の初期状態（どんなデータが表示されている状態か）
- **When** → ユーザーのインタラクション（何をクリック/入力するか）
- **Then** → インタラクション後の画面状態（何が変わるか）

## エッジケース画面の設計

すべての画面に対して、以下のエッジケースを検討する：

| エッジケース | 設計パターン |
|------------|------------|
| データ0件 | 空状態画面（アイコン + メッセージ + CTA） |
| ローディング中 | スケルトンスクリーンまたはスピナー |
| エラー発生 | エラーメッセージ + リトライボタン |
| 権限なし | アクセス拒否画面またはグレーアウト |
| 大量データ | ページネーション、仮想スクロール |
| 長いテキスト | 省略表示（...）+ ツールチップまたは展開 |

エッジケース画面は必ずしもモックアップとして生成する必要はないが、
インタラクション仕様で振る舞いを定義しておく。
